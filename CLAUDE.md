# EA-System

Django 5.2 + PostgreSQL multi-tenant accounting SaaS for Indonesian MSMEs. See README.md for architecture.

- Run tests: `.venv/bin/pytest` (settings: `config.settings.test`; uses `--reuse-db`, add `--create-db` after model changes)
- Dev server: `.venv/bin/python manage.py runserver`; region list: `manage.py load_regions` (after `migrate`); demo data: `manage.py seed_demo`
- PostgreSQL 18; `msme_user` owns `msme_db` (required to create tables in `public`) and needs CREATEDB for the test DB. The app connects as data-only `msme_app` (`DATABASE_URL`); `migrate`, `createcachetable` and the test runner switch to the owner (`DATABASE_OWNER_URL`, `apps/core/db_roles.py`), and every `migrate` re-grants the app role. Any other command that changes the schema must call `use_owner_connection` too; never give the app role DDL or ownership.

Conventions:
- Business rules in `domain.py` (no ORM), writes in `services.py` (atomic, raise `apps.core.exceptions.DomainError`), reads in `selectors.py`. Views stay thin.
- Every tenant query goes through `Model.objects.for_organization(org)`; views get the org from `OrganizationMixin`/`WriteMixin`/`ManageMixin`.
- Invoices, invoice lines, payments and PPh Final payments are guarded by DB triggers like the ledger (invoicing 0004, taxes 0006): change them only through their services (draft edit/delete, issue, record/void payment, void invoice, `create_return`, cancel PPh = void). The Faktur Pajak number can be set once after issue (`record_tax_invoice_number`, invoicing 0014). A sales invoice may carry a PPN facility (07/08, `services.Facility`; PPN computed into `vat_not_collected`, never charged). Receipts may record what the buyer withheld (`vat_withheld` for VAT collectors, `services.IncomeTaxInput` for PPh 22/23/Final; invoicing 0016); PPh Final withheld reduces that month's deposit (`PphFinalPayment.withheld`); a sales return leaves out PPN/PPnBM the collector still holds (`ReturnNote.vat_withheld`) and a refund gives back its share of withheld income tax (`ReturnNote.income_tax_withheld`; one kind per invoice). PPnBM (`TaxRate.luxury_rate`) posts to the `LUXURY_TAX` system account; Faktur codes follow `coretax.transaction_code` (DJP's priority). Payments to suppliers may withhold PPh 23/4(2) (`IncomeTaxInput(base, rate)`, credited to its payable); `taxes.WithholdingDeposit` (taxes 0012, guarded like PPh Final payments) settles a month, after which that month's withholdings are frozen; the bukti potong number is set once (`record_withholding_slip`, invoicing 0018). Sales invoices may come from a `tenants.BusinessPlace` (its NITKU/address are snapshotted); `assets.services.dispose_asset(sale=InvoicedSale(...))` issues the asset's code-09 invoice. Coretax XML (`apps/invoicing/coretax.py`) follows DJP's converter v1.6 samples; keep tag order. Returns (`ReturnNote`, invoicing 0011/0013) change only by `void_return` (posted -> void); `amount_credited` must equal the posted returns, and status follows paid + credited (`balance_due` subtracts both). Never delete or edit issued documents; `amount_paid`/status must match posted payments. Issued invoices carry party snapshots (`snapshot_parties()` at issue; templates use `party_*`/`seller`, never `invoice.contact.*`/`invoice.organization.*` for document details). Tax rates used on issued invoices only change `is_active` (taxes 0007); used items can't be deleted. Accounts with posted lines keep `Account.FIXED_ONCE_USED` + system_role; system accounts are permanent (ledger 0008); posting snapshots `account_code`/`account_name` onto lines in the DB trigger (ledger 0009), so show posted lines with `line.account_label`; invoice lines get the same snapshot at issue, plus the tax rate's name/rate/DPP and the item code (invoicing 0006-0008, `InvoiceLine.account_label`/`tax_label`/`item_label`); organization deletion removes accounts inside the purge function. Subscription invoices are guarded too (billing 0006): terms fixed at insert, set everything known at creation in the INSERT (e.g. `coverage_value` for credit switches), status only forward, payment/coverage written once when paid.
- All ledger postings go through `ledger.services.create_journal_entry`. Never edit/delete posted entries; reverse them. The database enforces this (triggers in `ledger/migrations/0004_immutable_ledger.py`): entries are inserted as drafts and posted by a `draft -> posted` update that checks balance, tenant and lock date; posted entries/lines raise `IntegrityError` on update/delete. Tests must create posted entries through the service (or insert a draft, add lines, then post). Posting appends to a DB-computed hash chain (`posting_sequence`, `previous_hash`, `entry_hash`, migration 0006; never set them in code) and records `posted_by`; `verify_ledger` checks it. To simulate tampering in tests, `SET CONSTRAINTS ALL IMMEDIATE` before disabling triggers. Only `purge_organization_ledger` may delete posted entries. It calls the `ledger_purge_organization` SQL function, which only the owner may execute, so organization deletion runs from `manage.py delete_organization` (owner connection), never from views or the admin.
- Addresses (README "Addresses"): models inherit `regions.models.Address` (street `address` + `village` FK to the Kemendagri list; `region_line`, `postal_code`, `full_address`); forms add `regions.forms.RegionFieldsMixin` (cascading selects, `static/js/regions.js`; override `address_required` for addresses abroad). Never add free-text city/province/postcode fields. Region tables are shared reference data written only by `manage.py load_regions` (owner; the app role may only read them); tests load real rows with the `regions(...)`/`jatake` fixtures.
- Language policy is in README "Languages"; follow it. URLs are English and language-neutral; never put the language in the URL.
- Interface text: English source strings, always marked for translation (`gettext_lazy` for module-level/labels/choices, `gettext` for runtime messages, `{% translate %}`/`{% blocktranslate trimmed %}` in templates). Use `%(name)s` placeholders, whole sentences, `ngettext`/`{% blocktranslate count %}` for anything counted, `pgettext` for ambiguous short words. Then `makemessages -l id`, translate in `locale/id/LC_MESSAGES/django.po`, `compilemessages`, commit .po and .mo (a test enforces this).
- Fixed sets of values are enumerations, never bare strings: `models.TextChoices` for anything stored, shown or filtered (nested on the model, or in `domain.py` when rules need it, e.g. `InvoiceStatus`, `AgingBucket`), `StrEnum` for internal/external codes (`PaymentStatus`, `ThrottleScope`, Xendit `SessionStatus`). Validate request values with `choice_param(..., Enum.values)`. Templates compare against members (`invoice.status == invoice.Status.PAID`, `invoice_kinds.SALES` from the invoicing context processor, or an enum passed in the view context), never quoted values (a test enforces it).
- Money: `|rupiah` in templates, `apps.core.formatting.localized_rupiah` in messages (separators follow the active language). Customer-facing documents render in `Contact.document_language`.
- SAK EMKM (README "SAK EMKM"): keep the accrual basis (record income/expenses in the period they arise, never on payment), present comparatives (`reports.views.balance_sheet`/`income_statement` build both columns), and keep the notes (`templates/reports/notes.html`) true to what the system does when posting rules change. PPh Final: `accrue_pph_final` posts expense/payable at month end; `record_pph_final_payment` settles that accrual (taxes 0009 guards both).
- Inventory (`apps/inventory`): items with `track_inventory` are perpetual. `invoicing.services.issue_invoice`/`void_invoice` call `inventory.plan_*` before posting (sales add the cost-of-goods-sold lines to the invoice entry) and `inventory.record` after; adjustments go through `inventory.services.adjust_stock`. Valuation replays `StockMovement` in `id` order (`inventory.domain.Stock`); never write movements directly (inventory 0002 guards them and an item's tracking once stocked). Tests that sell tracked items must stock them first (purchase or adjustment).
- Fixed asset register (`apps/assets`): registering posts nothing (the purchase is a bill/journal); `services.post_depreciation` posts each ended month once (one entry per month, dated its last day, source `fixed_asset`) and `dispose_asset` posts the disposal; `revise_estimate` records a prospective change of useful life/residual value/method (`AssetRevision`, append-only, assets 0004-0005; `FixedAsset.useful_life_months`/`residual_value`/`method` stay the original, use `current_*`); never write `DepreciationPosting` or asset figures directly (assets 0002 guards them, the purge function removes them). Schedules are pure (`assets.domain.depreciation_schedule`). `post_depreciation` runs nightly from cron.
- Stored business data (chart of accounts, journal descriptions, tax-rate/plan names) stays Indonesian (UU KUP Art. 28(4)) and is never translated.
- Plan changes only happen through `apps.billing` (payment confirmed by re-fetching the gateway, never by trusting a webhook body or redirect). `tenants.services.set_subscription` is the single writer of `Organization.plan`/`plan_paid_until`. Dev/tests use `BILLING_GATEWAY=fake`. Scheduled jobs (`process_billing`, `post_depreciation`, `prune_security_logs` and `verify_ledger` daily) live in `deploy/cron/crontab` and run through `deploy/cron/run.sh`; add new periodic commands there and reinstall with `deploy/cron/install.sh`.
- Input handling: forms inherit `apps.core.forms.BaseForm`/`BaseModelForm` (sanitizes text; a test enforces it); passwords use `strip=False`. Put format rules on model fields (`apps.core.validators`), use `BusinessDateField` for transaction dates and `DigitsField` for NPWP/NIB-style identifiers. Read request parameters only via `apps.core.params` (`text_param`, `choice_param`, `int_param`, `year_param`). Never use `|safe`/`mark_safe`/raw SQL; pass CSV cells through `csv_safe`.
- REST API (`apps/api`): function views under `/api/v1/` wrapped in `@endpoint(...)` (key auth, role check by method, throttle, JSON errors); call services, never write models directly. Keys (`ApiKey`) are keyed hashes; the key creator's membership decides access. Team invitations (`tenants.Invitation`) store token hashes only. Automatic renewal (`billing.AutoRenewal`, token encrypted) is charged by `process_billing` through `services.charge_auto_renewals`.
- Payroll (`apps/payroll`): `domain.py` holds the PP 58/2023 TER tables, PTKP, Art. 17 and BPJS rules (pure); `services.run_payroll` posts a month (one posted run per month), `pay_salaries`/`pay_bpjs` once each, `void_payroll` only while unpaid and before later runs/the PPh 21 deposit; runs and payslips are guarded (payroll 0002) and purged first. PPh 21 is deposited through `taxes.WithholdingDeposit` (kind `pph21`, `withholding_due` reads payroll); non-resident employees bear PPh 26 (`TaxScheme.PPH_26`, `PayrollRun.pph26`, deposit kind `pph26`, `SystemRole.PPH_26_PAYABLE`). Each payslip snapshots its `tax_scheme` (monthly/daily TER, year-end, PPh 26), `annualized` and `without_tin`; `selectors.annual_statement` rebuilds the 1721-A1 from the year's payslips with the same `services.year_end_tax`, so keep them in step. Severance (`Payslip.severance_tax`, PP 68/2009) is final within two calendar years of its first payment and Art. 17 (not final, `severance_final=False`) from the third; it stays out of the year-end calculation and the 1721-A1, and a former employee (`Employee.left_before`) is paid only severance (`TaxScheme.SEVERANCE_ONLY`); a tax allowance comes from `domain.gross_up`; `PriorIncome` (a previous employer's 1721-A1) is fixed once the year's last payslip is posted (`services._ensure_year_open`). PPh 21 on a non-employee's fee is a supplier-payment withholding (`IncomeTaxWithheld.PPH_21`, no rate: `payroll.domain.non_employee_pph21`; invoicing 0020).
- Coretax sending (`invoicing/coretax_api.py` adapters, `coretax_sync.py` services, `CoretaxConnection` with an encrypted token, `CoretaxSubmission`): numbers that come back are recorded through `record_tax_invoice_number` (subscription invoices: `billing.coretax.record_numbers`); `sync_coretax` runs from cron. eBupot files (`taxes/ebupot.py`: BPMP, BP21, BP26, BPA1, BPPU) follow DJP's converter XSDs (keep element order; `taxes/tests/test_ebupot.py` pins it); their records are mapped back by position (`CoretaxSubmission.records`) and numbered through `payroll.services.record_slip_number`/`invoicing.services.record_withholding_slip`. Exports (PEB) and bills equivalent to a faktur are `Invoice.special_document` (number/date set once, invoicing 0023; exports carry no PPN lines); imports are `taxes.ImportDeclaration` (PIB, guarded, counted as input PPN in `vat_summary`); their Dokumen Lain files come from `coretax.month_exports`/`month_special_inputs`/`month_special_returns`. Final PPh deposited on one's own income is `taxes.SelfDeposit` (expense + deposit entries, BPSP); PPh 26 on supplier payments is `IncomeTaxWithheld.PPH_26` (BPNR, deemed % from `tax_objects.PPH_26`, treaty rate with the contact's certificate; invoicing 0024; a 0% treaty rate keeps kind/rate/code with nothing withheld, invoicing 0026). A retailer's anonymous sales go out as the SPT Masa PPN digunggung file (`coretax.month_retail`/`build_retail_xml`, DJP's retail template; amounts share `coretax.line_amounts` with the Faktur). Supplier withholdings carry `Payment.income_tax_object` (DJP codes in `taxes/tax_objects.py`, generated; rate must match), set once later via `record_tax_object` (invoicing 0021).
- Login is rate limited by django-axes (email+IP, see README). Tests must log users in with `client.force_login`, not `client.login()` (axes needs a request). `AXES_USERNAME_FORM_FIELD` must stay `"username"` (what Django's login form passes to `authenticate`).
- CAPTCHA (`apps/accounts/captcha.py`, Cloudflare Turnstile, one `CaptchaAction` per form): sign-in requires it after `LOGIN_CAPTCHA_AFTER_FAILURES` failures per IP or email (`LoginForm.clean` verifies before authenticating); sign-up, password reset, resending the confirmation link, changing the unconfirmed email, changing the password, turning 2FA on or off, creating new backup codes, the 2FA step-up for an existing session and the sign-in 2FA code step always require it, before anything else (`CaptchaFirstFormMixin`, which takes `request`; the resend view checks it directly). Tests use `CAPTCHA_BACKEND=fake`: sign-up, reset, resend, change-email, change-password, 2FA setup/disable/step-up/sign-in code and backup-code posts, and tests that fail sign-ins repeatedly must include `RESPONSE_FIELD: FAKE_PASSING_TOKEN`. The admin login redirects to the site login (no second login form). The shared `fresh_cache` fixture clears throttle counters between tests.
- Password reset uses Django's views with project templates; links are built from `SITE_URL` (never the Host header). Throttles use `apps.accounts.throttle` on the shared cache. Emails to a user are rendered in `user.language`.
- Account enumeration (README "Account and record enumeration"): never answer differently for a registered and an unknown address. Sign-up doesn't sign in and always ends on `accounts:signup_done` (existing accounts get `services.send_account_exists_notice`); sign-up and password reset run inside `core.timing.minimum_duration(ACCOUNT_RESPONSE_MIN_SECONDS)` (0 in tests); an unconfirmed user's corrected address is `User.pending_email` until its link is opened; team members are always invited by link. Tests sign the new owner in with `force_login` after signing up. Look records up only through the organization's querysets (404 for other tenants). URL action segments are `StrEnum`s checked before use; API filters go through `_filter`, numbers through `_decimal(digits=...)`.
- Email verification is mandatory: `EmailVerificationMiddleware` redirects unverified users to `accounts:verify_email_pending`. Test users must be created with `email_verified_at=timezone.now()` (the shared fixtures do this). New views an unverified user must reach go into `EXEMPT_ACCOUNT_VIEWS`.
- 2FA uses django-otp (`apps/accounts/two_factor.py`); the login view stops after the password when 2FA is on (`two_factor.begin_login` → `accounts:login_otp`). The admin is an `OTPAdminSite`. In tests, compute codes with `django_otp.oath.TOTP` and let back-off pass by patching `django_otp.models.timezone.now`.
- `Organization.require_two_factor` is enforced by `apps.tenants.middleware.TwoFactorRequirementMiddleware` (checks `request.user.is_verified()`); views a member must reach before completing 2FA go in its `EXEMPT` set.
- Remembered devices (`apps/accounts/trusted_devices.py`) skip only the code step and are bound to `user.get_session_auth_hash()`. In tests sign out via the logout view, not `client.logout()` (which also wipes the remember cookie).
- 2FA devices are `accounts.AuthenticatorDevice` (Fernet-encrypted key) and `BackupCodeDevice`/`BackupCode` (keyed hashes); never use django-otp's `TOTPDevice`/`StaticDevice` (plaintext). Encryption/hashing goes through `apps.core.crypto` with `FIELD_ENCRYPTION_KEYS`.
- Plan switches are prorated in `apps.billing` (`switch_credit`, `switch_quote`): PPN on the net amount, free switches when credit covers the price, `superseded_on` prevents reusing credit. Billing tests that pay then switch must `refresh_from_db()` the organization.
- Change history / audit trail (README "Change history"): the database records every insert/update/delete of the tenant tables in `audit.RecordChange` (trigger `audit_record_change()`, audit 0010; SECURITY DEFINER, the app role can't write it; append-only, hash-chained per organization, `verify_audit_trail` daily). New tenant tables need `track_sql(...)` from `audit/migrations/0010_audit_trail.py` in their migration (a test enforces it); leave secrets out via its extra arguments. Who: `apps.audit.context` (`AuditActorMiddleware` for requests, `set_actor` e.g. in the API, `command:<name>` for commands). `core.DocumentSequence` (count up by one, never deleted), `payroll.PriorIncome` (fixed once the year is settled) and `invoicing.CoretaxSubmission` (kept as sent) are guarded too; organization deletion lifts these guards only through `ledger_purge_organization` (`audit_erasing`).
- Audit log (`apps/audit`): record sensitive actions with `audit.services.record(AuditAction.X, request=..., organization=..., target=..., **details)` after they succeed (sign-ins come from auth/axes signals). New actions need an `AuditAction` member and a category in `ACTION_CATEGORY` (a test enforces it). Never put secrets in details. Events are append-only in the database; only the owner can prune (`prune_security_logs`): account events and axes access logs after `SECURITY_LOG_RETENTION_DAYS` (90), organization/billing/system events (`KEPT_LONGER`) after `ORGANIZATION_LOG_RETENTION_DAYS` (3650), with their IP/browser blanked after 90 days (only the owner may blank; any other edit is rejected).
- Books export (`apps/reports/exports.py`): every tenant table must be listed in `TABLES` (a test enforces it), so add new tenant models there. Exports run in one REPEATABLE READ snapshot; `delete_organization` requires `--export-to` or `--skip-export`.
- Tests must not rely on data migrations (transactional tests flush the DB); create needed rows in fixtures.
